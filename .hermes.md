# hermes-trader — agent instructions

Auto-loaded for every Hermes session in this repo (cwd up to the git root).
Keep this lean — it's injected into the system prompt. Deep reference lives in
`.hermes/PROJECT.md` (handoff doc) and the `hermes-trader-*` skills.

## Follow-ups & watch items → register in `.hermes/WATCHLIST.md`

This repo keeps a **gitignored register** of future follow-ups, watch items, and
pending decisions: **`.hermes/WATCHLIST.md`** (in `.hermes/`, which `.gitignore`
excludes). It is the single source of truth for "check on this later".

**Standing rule — every session, not just scheduled ones:**
When your work surfaces anything that should be tracked beyond the current turn —
a watch item ("does the newly-unlocked non-major fills hold quality?"), a pending
decision (a shadow gate accruing data that needs a promote/die call), a known risk,
an open bug, or a "happening now" signal — **append/update it in `.hermes/WATCHLIST.md`**:
- Put it in the right section (§B active watches, §C pending decisions, §D resolved,
  or §E ops notes). If it's a new kind of item, add a short subsection.
- Record **how to check it** (the exact command + a baseline number + the timestamp it
  was observed), and **what "done / bad" looks like** (the resolve or escalate trigger).
- If it's time-sensitive (e.g. "re-check tomorrow"), either note the anchor date or
  back it with a cron job (see "Maintenance" below). Prefer the existing watchlist-scan
  job over creating a new one.
- **Do not** let a follow-up live only in chat or only in a session's todo — if it
  matters past this turn, it goes in the file.
- Mark an item resolved in §D **only with cited evidence** (command + number + date).

## Maintenance
- A cron job, **`hermes-trader watchlist scan`** (job id `65f58e83d190`, 07:00 UTC
  daily, terminal-only, `deliver: all`), **owns the file**: each run re-checks
  §A/B/C/D against the live container + git + all rotated logs, updates counts in
  place, and moves decision-ready items to §D with cited evidence. New items added
  by hand are picked up automatically — **no new cron job needed per item**.
- The cron job may *read* the bot/repo but **never writes config or bot code** and
  never restarts the container. Interactive sessions have the same boundary for the
  file itself (it is a register, not a trigger).

## Hard invariants (this repo)
- **Config**: versioned in the private sibling repo **`~/src/hermes-trader-config`**
  (`git@github.com:PsychoLogicAu/hermes-trader-config.git`). Canonical flow for ANY
  `.agent-config.json` change: edit in that repo → `scripts/deploy.sh "why: <context>"`
  (timestamped backup + inode-preserving copy to this repo's live file + verify + commit/push).
  Never checkout/symlink/mv over the live file (inode trap; container bind-mounts it,
  hot-reload ~60s). Editing the live file directly is allowed only as emergency — then run
  `scripts/deploy.sh`-equivalent backup AND sync the config repo immediately so drift
  (`config repo/scripts/check_drift.sh`) doesn't persist. `.env.local` NEVER goes in the
  config repo (real keys). Code changes need a container recreate — prove the rebuild delta
  = only the intended hunks before force-recreate.

  HL-rate-contention fixes). 0 failures = healthy; any failure = new, investigate.
