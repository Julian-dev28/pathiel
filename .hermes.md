## Follow-ups & watch items → register on the kanban board `hermes-trader`

**Since 2026-10-15 the source of truth for "check on this later" is the Hermes
kanban board `hermes-trader`** (SQLite at `~/.hermes/kanban/boards/hermes-trader/`).
`.hermes/WATCHLIST.md` is RETIRED (pointer stub only) — everything from it
(§A anchors, §B/§C watches, §D resolved evidence, §E ops notes) was migrated
2026-10-15 via `~/.hermes/scripts/hermes_trader_watchlist_migrate.py`.

**Standing rule — every session, not just scheduled ones:**
When your work surfaces anything that should be tracked beyond the current turn —
a watch item, a pending decision, a known risk, an open bug, a "happening now"
signal — **create a task on the board**:
- `hermes kanban --board hermes-trader create "<ID — short title>" --body-file <evidence.md>`
  (write the evidence to a temp file: **how to check it** = exact command +
  baseline number + observation timestamp, and **done/bad** = resolve/escalate trigger).
- Status semantics: `ready` = accruing/periodic · `schedule <id> "re-check ~<date>: <what>"`
  = waiting on time · `block <id> "decision owed: <question>"` = owner decision ·
  `complete <id> --result "<cited evidence>"` = resolved (this IS the new §D —
  complete only with command + number + date).
- Record check results as `comment <id> "<result + command + number + date>"`.
- **Never assign a profile** unless you deliberately want the dispatcher to spawn
  an agent worker (token policy: tracking board stays unassigned).
- §A live anchors = task `A — LIVE ANCHORS` (living document; replace its body
  with `edit`/re-create on each full scan).
- Do NOT let a follow-up live only in chat or a session todo — if it matters past
  this turn, it goes on the board.

## Maintenance
- The old `hermes-trader watchlist scan` cron (job id `65f58e83d190`, PAUSED)
  targeted the retired file. If a scan job is ever resumed it must target the
  board: re-check open tasks against live container + git + rotated logs, post
  results as comments, `complete` with evidence what's resolved, and refresh the
  `A — LIVE ANCHORS` body. New items added by hand are on the board already —
  **no new cron job needed per item**.
- Any scan may *read* the bot/repo but **never writes config or bot code** and
  never restarts the container. Same boundary for the board itself: it is a
  register, not a trigger.

## Hard invariants (this repo)
- **Config**: versioned in the private sibling repo **`~/src/hermes-trader-config`**
  (`git@github.com:PsychoLogicAu/hermes-trader-config.git`). Canonical flow for ANY
  `.agent-config.json` change: edit in that repo → `scripts/deploy.sh "why: <context>"`
  (timestamped backup + inode-preserving copy to this repo's live file + verify + commit/push).
