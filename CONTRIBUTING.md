# Contributing to pathiel

Bug reports, fixes and small features are welcome. Open an issue first for
anything that changes how orders are placed, sized or protected.

## Dev setup

> Maintainer path: this runs mainnet with the tracked repo config (20x, whole-equity sizing). It is not the public install.

A checkout is the maintainer's own setup. Never put a funded mainnet key in a
dev checkout; use read-only mode (no key) or a testnet API wallet.

```bash
git clone https://github.com/Julian-dev28/pathiel
cd pathiel
python3 -m venv .venv
.venv/bin/pip install -r requirements.lock
.venv/bin/pip install -e . --no-deps
scripts/install_hooks.sh
```

Python 3.11 or later; CI runs 3.11, 3.12 and 3.13. To try your change the
way a user gets it, load the plugin from your checkout for one session with
`claude --plugin-dir .`: that runs the public launcher `scripts/pathiel-mcp`,
not the repo `.mcp.json`.

## The gate

```bash
PATHIEL_STATE_DIR="$(mktemp -d)" .venv/bin/python -m pytest -q --no-header -p no:cacheprovider
.venv/bin/python -m ruff check .
```

The gate is offline: the root `conftest.py` refuses every non-loopback host,
so no test can reach Hyperliquid or place an order. It runs in
`scripts/hooks/pre-commit` on every commit. Never skip it with
`--no-verify`; fix what fails.

Other lanes, not part of the gate:

```bash
.venv/bin/python -m pytest -m online      # read-only tests against the live API
.venv/bin/python -m pytest -m browser     # Playwright, the Desk page
.venv/bin/python scripts/mcp_smoke.py     # live, read-only MCP smoke
```

Every change ships with its tests in the same pull request. A bug fix
ships with the test that would have caught it.

## The operator-path rule

pathiel runs two ways from the same code: the public install (plugin,
launcher, container; `PATHIEL_INSTALL=public`) and the maintainer's own
checkout, which trades real money today. A change must leave the
maintainer path byte for byte the same unless the change is about it.

- Put new behavior behind `contracts.runtime.is_public()` or a network
  check. `contracts/runtime/__init__.py` is the one place that answers
  "who is running, on which network".
- No new keyword on an SDK call for the maintainer, no new key in his tool
  outputs. `tests/test_operator_path_unchanged.py` and
  `tests/test_mcp_operator_unchanged.py` pin his instructions, tool list,
  thesis prompt and `.mcp.json` by hash.
- Never edit the tracked `.agent-config.json` in a feature change. The
  public defaults live in `config/public/`.
- Live-money tools (`place_bracket`, `bracket_sweep`, `set_target`,
  `close_position`, `set_leverage`, `cancel_order`) are only ever called
  against a mocked SDK in tests.

## Layout

```
pathiel/            FastAPI app, order placement (agents/bracket.py, client/exchange.py)
services/           one concern per folder: strategies, thesis, intel, llm, risk, accounts, auth
contracts/          shared pydantic models and the runtime contract
scripts/            MCP server, launchers, setup and approval scripts
config/public/      the public install's templates
tests/              the gate, evals (test_eval_*.py), online and browser lanes
```

Services talk through `contracts/`, never through each other's internals.
`docs/overhaul/MCP.md` is generated by `scripts/mcp_tool_table.py`; the
plugin's `skills/` and `agents/` copies by `scripts/build_plugin_skill.py`.
Edit the source, then regenerate.

## Style

- Direct, short, concrete. Name the file and function.
- No em dashes. No filler words; `tests/test_getting_started_doc.py` holds
  the banned list and the public copy lint reads it.
- No performance or return claims anywhere a user can read: README, docs,
  manifests. `tests/test_public_copy.py` lints them and every doc they
  link.
- Any instruction to clone the repo or start
  `scripts/pathiel-mcp-server.py` carries the maintainer-path warning above.
- Python: ruff clean, type hints on new functions, stdlib first.

## Pull requests

Use the template. Keep one concern per pull request, say which install path
it touches, and paste the gate's last line.

## Releasing

1. Bump the version in `server.json` (`version` and the image tag in
   `packages[0].identifier`), `.claude-plugin/plugin.json` and
   `pathiel/__init__.py`. `tests/test_listing_metadata.py` fails until all
   three agree. Add the `CHANGELOG.md` entry and
   `docs/RELEASE_NOTES_v<version>.md`.
2. Merge to `main`, then publish the plugin bundle from it:
   `python3 scripts/build_plugin_bundle.py publish --ref main --push`. That
   commits only the files the plugin runs (no CLAUDE.md, `.mcp.json`,
   `.claude/`, docs, tests or CI) to the `plugin` branch, which is what the
   Claude plugin directory tracks; it picks up the new `plugin.json` version
   from there. `tests/test_plugin_bundle.py` pins what goes in.
3. Tag `v<version>` on that commit and publish a GitHub release from the tag
   with the release notes as the body. Plugin users then get it with
   `claude plugin update pathiel@pathiel`.
4. Publishing the release starts `.github/workflows/release.yml`. It checks
   the versions agree with the tag and that the `plugin` branch holds the
   bundle of the tag (else it stops and prints the publish command), builds the MCP image natively on amd64
   and arm64, smoke-tests each over stdio (`initialize` answers with
   `serverInfo.version == <version>`, 60 tools, `place_bracket` refused
   read-only with no key), pushes `<version>` and `latest` for both, then
   publishes `server.json` to the official MCP registry with GitHub OIDC.
   No token or secret to set up. It is the only workflow allowed to write
   (`packages`, `id-token`), and `scripts/supply_chain_check.py` fails it
   if it ever runs on a push or pull request. To republish by hand: Actions,
   Release, Run workflow.
5. If a push is refused: package settings, Manage Actions access, give
   `Julian-dev28/pathiel` the Write role, re-run the failed jobs.

The website (GitHub Pages) is the `gh-pages` branch: the landing page in
`site/` and the scoreboard in `docs/scoreboard/`, nothing else. After a
change to either, including each pool build's `scoreboard.json`, publish it
from `main`: `python3 scripts/publish_site.py publish --ref origin/main --push`.
`tests/test_site.py` pins what it holds and the page's search metadata.

Manual fallback, from a checkout of the tag (needs `gh` with
`write:packages` and Docker running):

```bash
gh auth token | docker login ghcr.io -u Julian-dev28 --password-stdin
docker buildx build --platform linux/amd64,linux/arm64 -f Dockerfile.mcp \
  --label org.opencontainers.image.source=https://github.com/Julian-dev28/pathiel \
  -t ghcr.io/julian-dev28/pathiel-mcp:<version> \
  -t ghcr.io/julian-dev28/pathiel-mcp:latest --push .
mcp-publisher login github
mcp-publisher validate server.json
mcp-publisher publish server.json
```

The registry pulls the image to read its `io.modelcontextprotocol.server.name`
label, so the package must stay public.
